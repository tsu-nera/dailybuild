# 習慣

習慣管理の設計の正本。器は Toggl Focus（2026-11-26 に Habitica から移した）。
**Focus API の落とし穴は [docs/toggl.md](toggl.md) の「Toggl 2.0（Focus API）」節**にあり、
こちらは器に依存しない部分を持つ。

行動分析（Applied Behavior Analysis）の測定体系に寄せてあるが、**採らなかったものが
多い**ので、足したくなったら「意図的に持たないもの」を先に読むこと。

## 器を Toggl Focus にした理由

- Habitica は記録が 2026-10-05 で止まった。毎日押す Daily は、まれにしか起きない
  「減らす習慣」に合わず、押した時刻もあとから直せない
- Toggl Focus は毎日使っている。時刻をあとから直せ、`events.jsonl` で睡眠・運動と同じ
  時系列に並ぶので、習慣の前後の行動を分析できる

## データの層

| 層 | 実体 | 書き手 | 役割 |
|---|---|---|---|
| 打刻 | Toggl Focus のプロジェクトのエントリ（`data/toggl/focus_entries.csv`） | 本人 | 生起。時刻はあとから直せる |
| 対象 | Toggl Focus のクライアント（`data/toggl/focus_projects.csv`）+ `config/habits.yaml` | 本人 | 習慣1つ = プロジェクト1つ。クライアント `良い習慣` は増やす習慣、`悪い習慣` は減らす習慣 |
| 状態 | プロジェクトのアーカイブ（`archived_at`） | 本人（画面） | アーカイブ済みは表から外れる。記録は残る |
| 目標 | `config/private/habits.yaml` | 人 | 良い習慣のプロジェクト名 → `target_per_week` |
| 正規化 | `reports/events.jsonl` | script | 全ソースを1本の時系列に（#166） |
| 分母 | `reports/habits_daily.csv` | `habits.py build` | `date, habit, task_type, is_due, completed` |
| 介入 | `reports/habits/INTERVENTIONS.md` | agent | 何を試して何が分かったか |

**何を習慣として見るかは、対象クライアントに属するアーカイブされていないプロジェクトで決まる。**
`habits.yaml` に一覧を二重に持たない。足すのは `toggl.py project add <名前> [--bad]`、
外すのは画面でのアーカイブ（API ではアーカイブできない）。プロジェクトの削除は記録ごと
消えるので使わない。タグは使わない（Focus にはタグの作成・一覧の API が無い）。

`habits_daily.csv` が**ソース非依存の契約**。器を替えるときのコストは、
これを書くことと `events.jsonl` に行を出すことの2つだけになる（実際に Habitica から
Toggl へ替えたときもこの2つで済んだ）。Toggl 由来の行は `task_type=toggl`、`is_due` は空。

### 行を作る範囲（欠測の捏造を防ぐ）

行はプロジェクトを**観測できた日**にだけ作る: `max(created_at, 2026-10-27)` から、
アーカイブ済みなら `archived_at` の日まで、そうでなければ今日まで（JST 暦日）。
範囲内でエントリがある日は `completed=True`、無い日は `False`。範囲外の日は行を作らない。

- **起点を 2026-10-27（`lib.toggl.store.CUTOVER_DATE`）で切る。** Track から migrate した
  プロジェクトの `created_at` は移行時刻（2026-01-13）で、作った日ではない。Focus の
  エントリは切替日以降しか無いので、`created_at` から作ると約9か月の未観測期間が
  「不生起」として捏造される。切替日より前（Track の `time_entries.csv`）は読まない
- エントリとプロジェクトの対応は `project_id`（名前ではない。改名に強い）。`habit` 列は
  現在のプロジェクト名。エントリの日付は `start` の JST 暦日
- 今日の行は、まだ記録していないだけでも `False` になる。毎日全上書きなので翌日には直る

## 良い習慣と悪い習慣の見方

- **良い習慣**: 週の実施日数を `target_per_week` と比べる（下の「達成率と、目標の当て方」）
- **悪い習慣**: 週ごとに「7日中何日」起きたかを出すだけ。目標もクリアも持たない。
  減らす習慣はまれにしか起きないので、Habitica の Daily のように毎日押す形は合わなかった。
  起きた日にエントリを1つ作れば足りる（時刻はあとから直せる）

## 達成率と、目標の当て方

**達成率 = 実施日数 / 暦日数**（週なら7）。

**目標（`target_per_week`）は達成率の中に入れない。** 週の実施日数が
`target_per_week` 以上ならその週は**クリア**、という二値の判定に使う。週1回でよい
習慣なら `1/7` でクリア。

こうすると率の閾値（8割など）が設計から丸ごと消える。週4目標の達成率は 0 / 1/7 /
… / 4/7 の5値しか取らないので、率に閾値を当てると**目標が低い習慣ほど基準が厳しく
なる**。クリアの二値にすればこの歪みが起きない。

**その習慣の行が1件も無い期間は `-`**（まだ作っていない、または一度も観測して
いない）。`0/7` と書けば欠測の捏造になる。行があって未完了なら `0/7` でよい。
**欠測（行が無い）と不生起（行があって未完了）は別物。** セルの分母は行がある日数なので、
習慣を週の途中で作った週や進行中の週は `n/7` より小さい分母になる。

## CLI とスキルの境界

`habits.py show` は**計算機**で、判定しない。閾値も窓の長さもコードに持たせない。

| CLI が出す | スキルが判断する |
|---|---|
| 週ごとの `実施日数/行がある日数`（良い習慣は目標以上の週に `*`） | 目標の見直しの提示 |
| `clear`（クリアした完了週 / 観測できた完了週） | 介入するか |
| `target_per_week` の値 | |

**比較はするが判定はしない。** 実施日数と `target_per_week` の比較（`*` と `clear`）は
データどうしの照合で、閾値ではない。

`clear` の分母は**観測できた完了週の数**。習慣がまだ存在しなかった週は入らないので、
`2/2` は「2週しか観測していない」であって条件を満たした意味ではない。

進行中の週は `clear` に数えない（経過日数ぶんしか無い）。**`--weeks N` は進行中の週を
含むので、4完了週を見るには `--weeks 5`、12完了週なら `--weeks 13`。**

**設定とのずれは `show` が名指しで落とす。** (a) `target_per_week` の無い良い習慣、
(b) `config/private/habits.yaml` にあるのに良い習慣のアーカイブされていないプロジェクトに
無い名前（改名・アーカイブ・クライアント替え）。表を出したうえで名前を stderr に出し、
非ゼロで終わる。黙って対象から抜けるのが一番困る。

IRT（実施した日の間隔）は Habitica 時代の `habitica.py show` だけが出していて、
`habits.py show` はまだ出さない。

## 段（phase）— 凍結中

**判定規則を決めていない。データが1件も無い状態で議論だけで決めようとして、
根拠が4回入れ替わったため凍結した。**

2026-09-09 時点で `habits_daily.csv` は12行、クリアした週は 0、習慣は前日に作った
ばかり。「4完了週すべてクリア」なのか「直近5完了週のうち4週」なのか「通算12週」なのか
を照合できる相手が無く、議論はいくらでも蒸し返せる。引き継ぎ資料の
「ベースラインなしに始めると以後すべての効果判定が主観になる」が、判定規則そのものに
当たっている。

動いた根拠を残しておく（同じ道を2回通らないため）。

1. 段ごとに測るものが違う（流暢＝**反応潜時**）→ 潜時は保留なので流暢を落とす
2. 段ごとに測るものが違う（流暢＝**押下時刻の変動性**）→ 3段
3. 変動性を却下したので「**操作的定義が無い段は持たない**」→ 2段
4. 「段が分かれる根拠は測度ではなく**その段で何が許されるか**」→ 3段

さらに「直近4完了週すべてクリア」は週粒度の streak と同型（5週目に落ちると昇格が
4週先へ戻る）で、この設計が拒否したはずのものだった。

### いま持っているもの

- `habits.yaml` の `phase` / `phase_started_at` は Toggl へ移したときに**廃止した**
  （値が全習慣 `acquisition` のまま一度も動かなかった）。決めるときは足し直す
- **agent は段の移行を提示しない**

### 決めるときに使えるもの

- **phase が無くても介入の可否は決まる。** 段の唯一の仕事は「この習慣に介入してよいか」
  のゲートだが、それは `clear` を見れば直接わかる。介入台帳の排他制約も段を見ていない。
  **段そのものが要るのかから問い直す**
- **21日は根拠が無い。** Maxwell Maltz が1960年に書いたものが一般化した俗説で、
  Lally et al. (2010) は中央値66日・範囲18〜254日としてこれを反証した側。ただし
  範囲がこれだけ広い以上、**中央値を閾値にするのは精度の錯覚**
- ベースライン期は段ではない。実験の局面（測定）と学習の段階（習熟）は別の軸で、
  ベースライン期かどうかは**介入台帳にその習慣の行が1つも無いこと**から導出できる
- **数週ぶんの `clear` の実際の動き**。これが凍結を解く条件

## 意図的に持たないもの

足したくなったときは、まずここを読む。

- **連続日数（streak）** — 行動ではなく結果。押し忘れ1回で折れるので、測れないものを
  指標にすることになる
- **時刻の変動性** — 時間帯は融通を利かせる前提（朝に無理なら夜にやる）なので、
  ばらつきが小さいことが良いことでもない。**実施は日付で数える**
- **反応潜時** — 機会時刻（schedule）を持たないと出せない。保留であって否定ではないが、
  「時刻指定より行動連鎖への接続を優先する」を採ると起点が消えるトレードオフが残る
- **強度 / 遂行量** — 習慣ごとに出所が違う。必要になった習慣だけ外部ソース
  （Hevy / `exercise.csv` / Toggl の区間）から `attrs` に入れる
- **場所** — ほぼ自宅で、変数として動かない
- **mastery / pleasure** — Beck の活動記録表由来で、**行動分析の測定次元ではない**。
  好みと強化子は別物で、主観評定は機能の証拠にならない。強化子の同定は
  「既存ログで高頻度の行動を候補にする（プレマック）→ 介入として随伴させる →
  頻度が上がったか見る」で、新しい列を1つも要さない
- **随伴性テーブル** — 「機能したか」の判定は介入台帳の verdict と同じものを指す。
  間欠スケジュール（VR）を実際に回し始めたら、比率の管理のために起こす
- **`current_criterion` の自動調整** — シェイピングの段そのもの
- **MO の新規記録** — 睡眠・疲労・気分は `reports/metrics_daily.csv` に既にある。
  空腹と社会的文脈はこの人にとって定数。**MO は記録の課題ではなく結合の課題**で、
  日付を主キーに join すれば条件別の生起率比較は書ける（行が溜まってから）
