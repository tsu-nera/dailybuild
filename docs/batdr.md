## 実装前に踏むと危ない点

原典を読まずに設計して食い違った箇所。**issue 本文より原典が優先する。**

- **Form 1 は1時間刻み22行（5am 開始・翌 5am まで）× 活動 / 楽しさ(0-10) /
  重要さ(0-10)、加えて末尾に「その日の総合気分(0-10)」1つ。** 時間ごとの気分
  評定は BATD-R で**意図的に削除**され、日1個に置き換えられた（短時間の微細な
  変化は報告できない、行動変化に対し気分は遅れる）。日1個は省略枠ではなく判断
- **負担が重い時に原典が許すのは「日数を減らす」であって粒度ではない**
  （週2〜3日・平日と週末を両方含める → 徐々に増やす）。1時間刻みの目的が
  「楽しくも重要でもない時間の**長さ**」の観測なので、ブロックに丸めると
  測りたい量が消える
- **自由記述を避ける公式の変種がある。** 低識字者向けに、活動を最大20個の
  番号付き語彙から選ぶ Form 1 Supplement が用意されている。選択式フォームは
  原典からの逸脱ではない
- **第4週以降、Form 1 は入力フォームでなく書き換え可能な予定表になる。**
  計画した活動を事前に時刻つきで記入し、実行したら丸、未実行なら線を引いて
  実際にやったことを書く。追記専用の Google Forms には構造的に載らない
- Form 2 の評定軸は活動ごとの楽しさ・重要さ（快・熟達 P/M ではない）。
  Form 3 は活動15個を難易度 1〜15 で並べるだけの1枚

下の「段と進入条件」以降は原典側の手続きで、実装とは独立に有効。ただし段0〜1が

Bull's Eye で価値の抽出を置き換える案が 2026-09-07 に出ている）。

### 段と進入条件（週番号で分岐しない）

暦の週で分岐すると、凍結や中断でずれた時に「記録が数日しか無いのに価値の
抽出へ進む」という一番避けたい失敗をする。**判定の入力は何が揃っているか**
にする。進行の記録は `reports/batdr/LEDGER.md`（private）。

| 段 | 進入条件 | やること |
|---|---|---|
| 0 | 台帳に開始日が無い | 原理の共有 → 記録開始 |
| 1 | 記録があるが、平日と週末をまたぐ1週間分に届いていない | レビューのみ。**何も変えない** |
| 2 | 1週間分そろった / 価値と活動リストが無い | 価値 → 活動15個 → 難易度 1〜15 |
| 3 | 難易度順がある / 計画が無い | 易しい1〜3個を記録に計画として書き込む |
| 4 | 計画の実施結果がある | レビュー → 未達成なら3分岐 → 次週の計画 |

段4がそのままループなので、第6〜12週という区切りは持たない。ゲートを
「暦で1週間」ではなく「平日と週末を含む記録期間を経た」にしてあるのは、
原典が負担に対して認めるのが日数の削減（週2〜3日）だからで、行数で切ると
原典とずれる。

悪化時の凍結も特別扱いにしない。段が進まないだけで、復帰時に減っていない。

### 未完了をどこまで見せるか

第4週以降は計画を先に書くので、**未実行は本人の目に見える**。これは #147 の
「未完了は測定するが本人には見せない」と衝突しない。

- 原典が求めるのは、個々の未実行について**何が起きたかを会話で扱うこと**
  （3分岐がそのための道具）。見えないと成立しない
- 禁じるのは**達成率・連続日数・未完了の件数**。集計されると自己批判の
  材料になる。記録の欠測を指摘するのも同じ理由で禁じる

### 記録がゼロだった週の扱い

原典に節がある。**週全体を思い出そうとしない。** セッション中に直近1〜2日
ぶんだけをその場で書き、そこからパターンを探す。ゼロの週は失敗ではなく、
原典に復帰手順のある状態。

### 気分記録（emotion）とは結合しない

BATD-R は**時間ごとの気分評定を意図的に削除した**手法で、理由は「行動の
変化に対して気分は遅れる」こと。時刻レベルで活動と気分を並べると
「散歩したのに気分は2のまま」という読みが出て、これは行動をやめる方向に
働く。

- **`emotion.csv` と `activity.csv` を timestamp で join しない。相関も出さない**
- 楽しさ・重要さは**活動への評価**であって状態ではない。気分（emotion /
  daily_morning）とは別の量として扱う
- 日次相関は既に null と分かっているので、結合をやめて失うものは無い

### 廃案（同じ設計を2回しないための記録）

- **朝／昼／夜の3ブロック案**（issue #113 本文）。入力が1日20〜40項目に
  なる負担を粒度で解こうとしたもの。原典が負担に対して許すのは日数の削減
  であって粒度ではなく、ブロックに丸めると測りたい「楽しくも重要でもない
  時間の長さ」が消える
- **活動1件＝1行の追記ログ案**（issue #148 の初回実装、2026-09-06 に廃止）。
  Google Forms 相当の追記専用の形。**第4週以降に Form 1 が予定表になると、
  「計画したが実行しなかった」を構造的に表現できない。** #147 の
  「未完了は測定するが本人には見せない」は未完了が記録に存在することが前提
  なので、測定対象そのものが無くなる。入力の摩擦を下げるために置いていた
  Apps Script（`activity_timestamp.gs`）もこの時に不要になった
- **Form 1 を週タブのスプレッドシートに置く案**（2026-09-06 実装 / 2026-09-07
  廃止）。原典の帳票をそのまま移した唯一の形で、実装は完成していた。
  止まったのは入力側で、記録は1日ぶん。上の「実装: 廃止」に詳細
