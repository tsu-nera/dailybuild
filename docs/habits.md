# 習慣

習慣管理の設計の正本。**器（Habitica）の落とし穴は [docs/habitica.md](habitica.md)**
にあり、こちらは器に依存しない部分を持つ。

行動分析（Applied Behavior Analysis）の測定体系に寄せてあるが、**採らなかったものが
多い**ので、足したくなったら「意図的に持たないもの」を先に読むこと。

## データの層

| 層 | 実体 | 書き手 | 役割 |
|---|---|---|---|
| 打刻 | Habitica の Daily | 本人 | 生起の瞬間。`ts` が押下時刻として残る |
| 正規化 | `reports/events.jsonl` | script | 全ソースを1本の時系列に（#166） |
| 分母 | `reports/habits_daily.csv` | script | `date, habit, task_type, is_due, completed` |
| 対象と状態 | `config/private/habits.yaml` | 人 | 何をレビューするか、目標、phase |
| 介入 | `reports/habits/INTERVENTIONS.md` | agent | 何を試して何が分かったか |

`habits_daily.csv` が**ソース非依存の契約**。Habitica を捨てるときのコストは、
これを書くことと `events.jsonl` に行を出すことの2つだけになる。

## 達成率と、目標の当て方

**達成率 = 実施日数 / 暦日数**（週なら7、月なら暦月の日数）。**`is_due` を分母に
しない。**

`is_due` は `repeat` の設定と cron の被覆で習慣ごと・期間ごとに動くので、分母に
すると期間どうしも習慣どうしも比較できない。`is_due` が持つのは分母ではなく被覆。

**目標（`target_per_week`）は達成率の中に入れない。** 週の実施回数が
`target_per_week` 以上ならその週は**クリア**、という二値の判定に使う。週1回でよい
習慣なら `1/7` でクリア。

こうすると率の閾値（8割など）が設計から丸ごと消える。週4目標の達成率は 0 / 1/7 /
… / 4/7 の5値しか取らないので、率に閾値を当てると**目標が低い習慣ほど基準が厳しく
なる**。クリアの二値にすればこの歪みが起きない。

**その習慣の行が1件も無い期間は `-`**（まだ作っていない、または一度も観測して
いない）。`0/7` と書けば欠測の捏造になる。行があって未完了なら `0/7` でよい。
**欠測（行が無い）と不生起（行があって未完了）は別物。**

**cron の被覆は見ない。** 完了の記録は cron に依存しない（タップした時点でエントリが
立ち、cron が書くのは未完了のプレースホルダだけ）ので、分母を暦日数にした時点で
被覆はどの数字にも効かなくなった。器の内部事情を判定から外しておくほうが、
Habitica を捨てるときにも素直になる。

`habitica.py cron` の実行自体は残す（走らないと未完了の Daily が締まらず HP も
動かない）。記録に使わないだけ。

## CLI とスキルの境界

`habitica.py show` は**計算機**で、判定しない。閾値も窓の長さもコードに持たせない。

| CLI が出す | スキルが判断する |
|---|---|
| `clear`（クリアした完了期間 / 観測できた完了期間） | 何期間そろえば昇格か |
| `target_per_week`・`phase` の値 | 昇格・降格の提示 |
| IRT（実施した日の間隔） | |

**比較はするが判定はしない。** 実施日数と `target_per_week` の比較（`*` と `clear`）は
データどうしの照合で、閾値ではない。何期間そろえば昇格かという規則はコードが知らない。

`clear` の分母は**観測できた完了期間の数**。習慣がまだ存在しなかった期間は入らないので、
`2/2` は「2期間しか観測していない」であって条件を満たした意味ではない。**分母が
移行条件の期間数に足りないうちは判定しない。**

進行中の期間は `clear` に数えない（経過日数ぶんしか無いので昇格が早まる）。**`--weeks N`
は進行中の週を含むので、4完了週を見るには `--weeks 5`、12完了週なら `--weeks 13`。**

**期間ごとの列は出さない。** 週を横に並べると窓を広げるたびに表が伸びて読めなくなる
（12週や13週で回す前提なので特に）。どの週が落ちたかは現在見えない。見せ方は未決。

## 段（phase）— 凍結中

**判定規則を決めていない。データが1件も無い状態で議論だけで決めようとして、
根拠が4回入れ替わったため凍結した。**

2026-09-09 時点で `habits_daily.csv` は12行、クリアした週は 0、習慣は前日に作った
ばかり。「4完了週すべてクリア」なのか「直近5完了週のうち4週」なのか「通算12週」なのか
を照合できる相手が無く、議論はいくらでも蒸し返せる。引き継ぎ資料の
「ベースラインなしに始めると以後すべての効果判定が主観になる」が、判定規則そのものに
当たっている。

動いた根拠を残しておく（同じ道を2回通らないため）。

1. 段ごとに測るものが違う（流暢＝**反応潜時**）→ 潜時は保留なので流暢を落とす
2. 段ごとに測るものが違う（流暢＝**押下時刻の変動性**）→ 3段
3. 変動性を却下したので「**操作的定義が無い段は持たない**」→ 2段
4. 「段が分かれる根拠は測度ではなく**その段で何が許されるか**」→ 3段

さらに「直近4完了週すべてクリア」は週粒度の streak と同型（5週目に落ちると昇格が
4週先へ戻る）で、この設計が拒否したはずのものだった。

### いま持っているもの

- `habits.yaml` の `phase` / `phase_started_at` は**フィールドだけ残し、全習慣
  `acquisition` のまま動かさない**
- **agent は段の移行を提示しない**

### 決めるときに使えるもの

- **phase が無くても介入の可否は決まる。** 段の唯一の仕事は「この習慣に介入してよいか」
  のゲートだが、それは `clear` を見れば直接わかる。介入台帳の排他制約も段を見ていない。
  **段そのものが要るのかから問い直す**
- **21日は根拠が無い。** Maxwell Maltz が1960年に書いたものが一般化した俗説で、
  Lally et al. (2010) は中央値66日・範囲18〜254日としてこれを反証した側。ただし
  範囲がこれだけ広い以上、**中央値を閾値にするのは精度の錯覚**
- ベースライン期は段ではない。実験の局面（測定）と学習の段階（習熟）は別の軸で、
  ベースライン期かどうかは**介入台帳にその習慣の行が1つも無いこと**から導出できる
- **数週ぶんの `clear` の実際の動き**。これが凍結を解く条件

## 意図的に持たないもの

足したくなったときは、まずここを読む。

- **連続日数（streak）** — 行動ではなく結果。押し忘れ1回で折れるので、測れないものを
  指標にすることになる
- **押下時刻の変動性** — Habitica の timestamp は「押した時刻」であって「やった時刻」
  ではなく、後から編集もできない。朝やって夜押した日は夜として残り、**忙しい朝ほど
  押し忘れて遅い方へ偏る**ので、標本を増やしても消えない系統誤差になる。そもそも
  時間帯は融通を利かせる前提（朝に無理なら夜にやる）なので、ばらつきが小さいことが
  良いことでもない。**IRT は日付で数える**
- **反応潜時** — 機会時刻（schedule）を持たないと出せない。保留であって否定ではないが、
  「時刻指定より行動連鎖への接続を優先する」を採ると起点が消えるトレードオフが残る
- **強度 / 遂行量** — 習慣ごとに出所が違う。必要になった習慣だけ外部ソース
  （Hevy / `exercise.csv` / Toggl の区間）から `attrs` に入れる
- **場所** — ほぼ自宅で、変数として動かない
- **mastery / pleasure** — Beck の活動記録表由来で、**行動分析の測定次元ではない**。
  好みと強化子は別物で、主観評定は機能の証拠にならない。強化子の同定は
  「既存ログで高頻度の行動を候補にする（プレマック）→ 介入として随伴させる →
  頻度が上がったか見る」で、新しい列を1つも要さない
- **随伴性テーブル** — 「機能したか」の判定は介入台帳の verdict と同じものを指す。
  間欠スケジュール（VR）を実際に回し始めたら、比率の管理のために起こす
- **`current_criterion` の自動調整** — シェイピングの段そのもの
- **MO の新規記録** — 睡眠・疲労・気分は `reports/metrics_daily.csv` に既にある。
  空腹と社会的文脈はこの人にとって定数。**MO は記録の課題ではなく結合の課題**で、
  日付を主キーに join すれば条件別の生起率比較は書ける（行が溜まってから）

## 未決

- **押し忘れが日付をずらす** — `dayStart: 5` なので前日ぶんを翌朝押すと、前日が
  「不生起」で確定し、翌日の「生起」として立つ。訂正できないだけでなく**間違った日に
  記録される**。週境界をまたぐと週次の回数まで動く。訂正オーバーレイを台帳で持つ案
  まで出ているが未決
