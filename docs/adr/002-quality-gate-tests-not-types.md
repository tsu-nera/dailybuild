# ADR 002: 品質ゲートは型チェッカーではなくテストに置き、対象を沈黙故障に限定する

- **Status**: Accepted (2026-09-05)
- **Deciders**: tsu-nera

---

## Context

このリポジトリの故障には共通の形がある。**例外を出さず正常終了する。**

- 取得が0件でも「データがありません」と出して成功終了する
- 欠測日を `0.0` として集計に入れる（睡眠負債が欠測週で膨張する）
- MoneyForward の未来日付の行（引き落とし予定日）を「最新」として読む
- 成分表の `-`（未測定）を 0 として扱う
- 期間置換が、取り替えるつもりのなかった日まで削除する

いずれも実行しても目視でも気づけない。しかも壊れた値が CSV に書かれた時点で
**元に戻せない**ものがある（Fitbit は過去の値を遡って書き換える、Tuya のログは
7日で消える、Toggl の削除済みエントリは原理的に復元できない）。

個人プロジェクトでありバグを報告してくれる利用者がいないため、気づく経路が
実質テストしか無い。一方で分析・レポートは探索的に方針が変わり続けるので、
そちらにゲートを置くと変更のたびにテストを直す作業が発生して足枷になる。

同じ判断を2回検討している（2026-08-27 と 2026-09-05）。3回目を避けるために
ADR に落とす。それまでの記録は agent の memory（リポジトリ外）にしか無く、
clone にも worktree にも付いてこないため、参照先として信頼できなかった。

---

## Decision

**型チェッカーは導入しない。品質ゲートは `uv run pytest tests -q` のみとし、
テストを書く対象は「欠測を捏造しないこと」「二重に入れないこと」の再発防止に
限定する。**

### 型チェッカーを採用しない理由

このリポジトリの故障は**型としては正しい値**で起きる。2026-09-05 に期間フィルタへ
故意に4つのバグを入れて確認した:

| 変異 | 型 | テスト |
|---|---|---|
| `start <= date` を `start < date` に | 通る | 落ちる |
| ページ打ち切りの `<` を `<=` に | 通る | 落ちる |
| 範囲判定の end 側を落とす | 通る | 落ちる |
| ページ打ち切りを削除 | 通る | 落ちる |

4件とも型チェッカーは検出しない。それでいて結果は「範囲外の日付が CSV に混ざり、
期間置換が別の日を消す」という最も戻せない形になる。実際に起きる故障に一度も
発火しないゲートを足す意味がない。

導入コストの実測（2026-08-27）: `ty check` で210件、うち大半は
`unresolved-attribute` 47 / `invalid-argument-type` 45 で pandas の型情報不足由来。
ゲートにすると agent が毎回ノイズで停止する。

### テストを書く対象

**書く**: マージ、期間置換、ID の型、冪等性、レート制限、symlink 未マウント。

**書かない**: レポートの文面、Jinja2 のレンダリング結果、分析の閾値・相関の解釈、
API クライアントの薄いラッパー。

判断基準は1問で足りる:

> **そのテストが防ぐ「CSV に書かれる誤った値」を1つ具体的に言えるか。**
> 言えなければ書かない。

### テストの規律はコストではないことの確認

「テストを書く」方針の負担を疑ったが、実測では成立しなかった。

| | 件数 | 所要 |
|---|---|---|
| 2026-08-27 | 120件 | 約37秒 |
| 2026-09-05（分離前） | 274件 | 約104秒 |
| 2026-09-05（分離後・既定） | 262件 | **約1.8秒** |
| 2026-09-05（分離後・`-m net`） | 12件 | 約74秒 |

件数を2倍以上にしても、外部 API を叩かないテストは合計2秒で終わる。長く感じて
いた所要はすべて net 側が占めており、テストの規律とは無関係だった（分離の運用は
CLAUDE.md「テスト方針」に記載。容易に戻せるので ADR には含めない）。

### 検討したが採用しなかった案

- **mypy / ty をゲートに追加する** — 上表のとおり実際の故障を1件も検出しない。
  ノイズ210件で agent が停止する副作用だけが残る
- **lint（ruff）をゲートに追加する** — `ruff check --select E9,F` で108件（84件は
  自動修正可）。ただし実バグに直結する `F821`（未定義名）は **0件**だったので、
  いま入れても得るものがない。将来入れるならこの狭いセットから
- **テストを書かない（個人プロジェクトだから）** — 逆。利用者がいないので
  バグを報告してくれる人もいない。気づく経路がテストしか無い
- **分析・レポートにもテストを広げる** — 探索のたびにテストを直すことになる。
  分析方針は変わり続ける前提なので、ここを固定すると探索が止まる

---

## Consequences

### 良い点

- 品質ゲートが1コマンドに収まり、約2秒で終わる。agent が変更のたびに回せる
- テストが「何を守っているか」を1文で言えるものだけに保たれ、腐らない
- 型エラーのノイズで作業が止まらない

### 注意点

- **型に起因するバグは検出されない。** pandas の dtype 取り違え（ID が int になる等）は
  テストで明示的に押さえる必要がある。実際 ID の型は「書く」対象に入っている
- **新しいテストは1つ壊して赤を見ること。** 通るだけのテストは何も守っていない。
  この ADR の根拠自体が変異テストで取った
- **テストの無い領域（レポート・分析）は壊れても気づけない。** これは受け入れた
  トレードオフであって、見落としではない。数値の妥当性はレビュー時の目視で見る
- 新しい取得先やマージ処理を足したらテストも足す。足さないと沈黙故障の穴が空く
