# 習慣

習慣管理の設計の正本。**器（Habitica）の落とし穴は [docs/habitica.md](habitica.md)**
にあり、こちらは器に依存しない部分を持つ。

行動分析（Applied Behavior Analysis）の測定体系に寄せてあるが、**採らなかったものが
多い**ので、足したくなったら「意図的に持たないもの」を先に読むこと。

## データの層

| 層 | 実体 | 書き手 | 役割 |
|---|---|---|---|
| 打刻 | Habitica の Daily | 本人 | 生起の瞬間。`ts` が押下時刻として残る |
| 正規化 | `reports/events.jsonl` | script | 全ソースを1本の時系列に（#166） |
| 分母 | `reports/habits_daily.csv` | script | `date, habit, task_type, is_due, completed` |
| 対象と状態 | `config/private/habits.yaml` | 人 | 何をレビューするか、目標、phase |
| 介入 | `reports/habits/INTERVENTIONS.md` | agent | 何を試して何が分かったか |

`habits_daily.csv` が**ソース非依存の契約**。Habitica を捨てるときのコストは、
これを書くことと `events.jsonl` に行を出すことの2つだけになる。

## 達成率の分母は `target_per_week`

**`is_due` ではない。**

Habitica の Daily は「週x回」を表現できないので、`repeat` を全曜日にして毎日 due に
してある。したがって `is_due` は常に週7で、週4目標の習慣は完璧にやっても
`4/7 = 57%` にしかならない。**8割の基準に永久に届かない。**

`is_due` が持つのは分母ではなく**被覆**——その日を観測できたか（cron が走ったか）。
役割が別。

**被覆が7日中5日未満の週は判定に使わない。** cron が走らなかった日は欠測であって
未達ではないので、達成率が実態より低く出る。除外して、条件を満たす週が揃うまで待つ
（前に詰めない）。

## 段（phase）

Instructional Hierarchy（Haring & Eaton, 1978）の獲得 → 流暢 → 維持。般化・適応は
採らない（般化は「別の場面でも出るか」で、場所を記録しないので測れない）。

**ベースライン期は段ではない。** 実験の局面（測定）と学習の段階（習熟）は別の軸で、
混ぜると「ベースライン期の流暢な習慣」が表現できなくなる。ベースライン期かどうかは
**介入台帳にその習慣の行が1つも無いこと**から導出できるので、状態として持たない。

**段ごとに測るものが違う。** 同じ達成率の閾値を上げていくだけなら段を分ける意味がない。

| 段 | 問い | 指標 |
|---|---|---|
| `acquisition`（獲得） | できるか | 達成率 |
| `fluency`（流暢） | 考えずに出るか（刺激性制御） | 押下時刻の変動性 |
| `maintenance`（維持） | 調子が悪くても出るか | MO 不良日の達成率 |

流暢さの実体は刺激性制御——特定の文脈で自動的に生起すること——なので、**時刻の変動性が
その操作的定義になる**。反応潜時は保留しているが、流暢期の判定は潜時なしで成立する。

## 移行

窓は ISO week で畳み、**完了した週だけ**を使う（進行中の週は経過日数ぶんしか無く、
必ず小さく出る）。ローリング日数窓にしない — `target_per_week` が週にしか定義されて
いないため。

| 移行 | 条件 |
|---|---|
| 獲得 → 流暢 | 直近**4完了週**の合計が目標合計の8割以上。**かつ 0 回の週が無い** |
| 流暢 → 維持 | 変動性が前の4週より増えていない状態が4完了週。押下が8点未満なら算出しない |
| 維持 → 卒業 | MO が悪い日でも達成率が落ちない。**当面は判定しない**（n が無い） |
| 降格（→ 獲得） | 直近**2完了週**の合計が目標合計の8割未満 |

週ごとに8割を課さないのは粒度の問題。週4目標だと達成率は 0 / .25 / .5 / .75 / 1.0 の
5値しか取らず、8割は実質「毎週4/4」を要求する。**目標が低い習慣ほど基準が厳しくなる**
のは筋が通らない。4週合計にすると週4で16回中13回、週7で28回中23回になる。合計だけだと
「3週満点＋1週ゼロ」が通るので、0の週を弾く条件を足す。

昇格に4週、降格に2週と長さが違うのは、安定の確認と異常の検出で必要な窓が違うため。

**降格させない例外**：複数の習慣が同時に落ちているとき。それは MO の問題で、個別の段を
動かすと当て所を外す。

**昇格・降格は人が `habits.yaml` を書き換える。agent は提示するだけ。** 自動で動かすと
シェイピングの段管理になり、BATD-R で捨てたもの（[docs/batdr.md](batdr.md)）に戻る。
手編集なら、なぜ動かしたかが commit に残る。

## 意図的に持たないもの

足したくなったときは、まずここを読む。

- **連続日数（streak）** — 行動ではなく結果。押し忘れ1回で折れるので、測れないものを
  指標にすることになる
- **反応潜時** — 機会時刻（schedule）を持たないと出せない。保留であって否定ではないが、
  「時刻指定より行動連鎖への接続を優先する」を採ると起点が消えるトレードオフが残る
- **強度 / 遂行量** — 習慣ごとに出所が違う。必要になった習慣だけ外部ソース
  （Hevy / `exercise.csv` / Toggl の区間）から `attrs` に入れる
- **場所** — ほぼ自宅で、変数として動かない
- **mastery / pleasure** — Beck の活動記録表由来で、**行動分析の測定次元ではない**。
  好みと強化子は別物で、主観評定は機能の証拠にならない。強化子の同定は
  「既存ログで高頻度の行動を候補にする（プレマック）→ 介入として随伴させる →
  頻度が上がったか見る」で、新しい列を1つも要さない
- **随伴性テーブル** — 「機能したか」の判定は介入台帳の verdict と同じものを指す。
  間欠スケジュール（VR）を実際に回し始めたら、比率の管理のために起こす
- **`current_criterion` の自動調整** — シェイピングの段そのもの
- **MO の新規記録** — 睡眠・疲労・気分は `reports/metrics_daily.csv` に既にある。
  空腹と社会的文脈はこの人にとって定数。**MO は記録の課題ではなく結合の課題**で、
  日付を主キーに join すれば条件別の生起率比較は書ける（行が溜まってから）

## 未決

- **押し忘れが日付をずらす** — `dayStart: 5` なので前日ぶんを翌朝押すと、前日が
  「不生起」で確定し、翌日の「生起」として立つ。訂正できないだけでなく**間違った日に
  記録される**。週境界をまたぐと週次の回数まで動く。訂正オーバーレイを台帳で持つ案
  まで出ているが未決
- **変動性の絶対閾値** — 実データが無いので相対条件（前4週より増えていない）にして
  ある。目盛りが見えてから検討する
