# 観察日記（reports/observation/）

agent が環境データから本人の行動を観察する記録（#209）。目的は2つ: 本人が読んでメタ視点の気づきを得ること、
生活改善を相談するときに時系列の材料が揃っていること。daily-review（健康）とは独立していて、
寝坊分析（`/early-rising`）のような課題別スキルはこれを読むレンズになる。

| ファイル | 書き手 | 更新 | 中身 |
|---|---|---|---|
| `YYYY-MM-DD.md` | `scripts/observation.py build`（vaio の日次） | 3日ぶん全上書き | データ源の状態・区切り・時系列・不明区間 |
| `YYYY-Wxx.md` | agent（週次） | 週1回 | 日をまたぐパターン。事実と日次ファイルへのリンク |
| `labels.csv` | agent（本人の申告を写す） | 追記 | 区切りの正解時刻 |

生活日は4時〜翌4時（`config/observation.yaml` の `day_start_hour`）。夜の区切り（帰宅・画面off・消灯・入眠）と
朝の区切り（最終覚醒・離床・出発・到着）はそれぞれの生活日に入るので、「ある夜から翌朝」は2ファイルにまたがる。

## 落とし穴

- **材料が欠けた区切りは空ける。** Fitbit の睡眠記録の終了は離床ではない（10-17 は 09:28、本人の離床は 10:05）。
  埋めずに「不明」のまま出すことで、何のセンサーが要るかが見える
- **スマホは最終受信時刻で生存を判定する。** Companion App / Tailscale が止まると画面 on のまま値が残る
- 生活音は不在中も -34dBFS 前後の塊が出る（外の音）。在宅の生活音は `activity_dbfs` 以上の塊として読む
- Remo の人感は不在中にも反応するので使わない。照明は自動化されうるので生活音と重ねて読む。照明・カーテンを自動化したら `config/observation.yaml` の `automated_since` に日付を書く（コードは変えない）。その日以降、帰宅・離床は生活音だけで取り、消灯は出さない（10-16〜19 の答え合わせでは生活音だけでも離床2分・帰宅1分のズレ）
- HA の材料は history API から毎回読む（`config/homeassistant.yaml` の CSV は保存用の写し）

## 改善の回し方

判定を変えるのは `config/observation.yaml` の閾値か `src/lib/observation/landmarks.py` のルール。

1. 本人が時刻を言ったら（「10:05 に布団から出た」）、`labels.csv` に1行足す。adb の usagestats のように
   本人以外の確かな記録も `source` を書いて足してよい
2. 判定を変えたら `uv run scripts/observation.py eval` で、変更前後の平均絶対誤差と「不明」の件数を比べる。
   悪くなった区切りがあれば戻す
3. 答え合わせの1件に合わせた閾値は他の日で外れうる。件数が少ないうちは eval の数字を過信しない

## 週次

`/weekly-review` の中で行う。

1. その週の日次ファイル7つを読み、日をまたぐパターンを `YYYY-Wxx.md` に書く（例: 帰宅→画面off が毎晩2時間超）。
   数字は日次ファイルからの引用に留め、原因は結論しない
2. 毎回「不明」になる区間・区切りを拾い、センサーで埋めるべきかを書く（センサー追加は saru9000 の担当）
3. `eval` のズレが大きい区切りは、閾値やルールを直して PR を出し merge まで進める
